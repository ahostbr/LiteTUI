## Change

`tasks.request_kill` and `tasks.attach_process` arbitrate the process-handle handoff with a short lock. No spawn, kill, disk access or other blocking work occurs under that lock. A Stop request marks a locally owned running shell task killed even before it has a process handle. A shell that has not started suppresses its spawn; if spawn was already in flight, the thread attaching the handle owns the single kill. If the handle arrived first, the existing app kill worker owns it.

Pending acceptance is limited to `bash` and `powershell`, the providers participating in this handoff. Foreign tasks, unowned persisted rows and pending non-shell/subagent/trusted-provider work are not reported killed. Existing process-backed cancellation retains its behavior. The task row's schema is unchanged; the synchronization lock is not serialized. Killed state is persisted through the existing app transition and retained when the background runner finishes.

The unchanged single-constructor `tasks.load` invariant had an unrelated stale line-number assertion (`app.py:1216` vs the baseline's actual `app.py:1251`). The exact structural assertion already reviewed for T719 is migrated here: it requires one call in `app.py` whose containing function is `__init__`. It does not permit another load or a different caller.

## Promotion follow-up — 706d33f held before merge

The 27-file result above validated explicit background starts. Further review found that a foreground shell could be promoted while spawn was pending: its thread still held foreground context and would attach to the global cancel slot, so a successful pending Stop could falsely report it killed. Candidate `706d33f` was explicitly held before merge. The deterministic test now covers both delay phases under both explicit background and actual timed auto-promotion. Both new promoted arms failed against that candidate: **`2 failed, 5 deselected in 10.76s`**, including a side effect after Stop and an uncollected late child (`pending-promotion-red.log`).

Each promotable call now receives a distinct `ProcessSlot`, carried through the async/thread context. Promotion transfers ownership of that exact slot to its task; process publication resolves the current owner atomically. There is no shared pending-task pointer that could attach two concurrent calls to the wrong owner. Pending cancellation also requires the local runner's non-persisted handoff registration, not merely a shell name on a task row.

A promoted call cannot overwrite or clear a newer foreground call's cancel slot. Its own confirmed kill result does not read the newer foreground call's unrelated confirmation flag. Hook completion consults the process slot's current task owner so cancellation is reported consistently after promotion. The tool still executes through the same single `asyncio.to_thread(fn, args)` door.

The expanded pending, background and RPC task tests pass together: **`31 passed in 13.15s`**, including preservation of a simulated newer foreground handle and its independent confirmation metadata (`pending-promotion-green-final.log`). Final verification retains the original 27 files and adds the two symbol-derived affected files `test_hook_boundaries.py` and `test_bash_tool_git_bash.py`, giving 29 named files. The list/command are recorded as `pending-promotion-gate-files.txt` and `pending-promotion-gate-command.txt`; final results follow below.
